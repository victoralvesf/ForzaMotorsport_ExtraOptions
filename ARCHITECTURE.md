# Architecture

This document explains how the mod makes Forza Motorsport 5 run on Azimuth. It describes the
design in our own words. It contains no code from Azimuth or from the game.

## Background

Azimuth (Almost There Games) is an Xbox One -> PC translation layer. It loads the original
Xbox One executable into its own process with its own PE loader, and resolves the game's imports
to its own high-level implementations of the console libraries: kernel, COM/WinRT, Direct3D 11.X
(implemented on top of Direct3D 12), XAudio2, XMA decoding and so on.

Azimuth officially runs only Forza Horizon 2 and FH2 Fast & Furious. Forza Motorsport 5 uses the
same engine (ForzaTech), but it was built with an older Xbox One XDK (November 2012) than FH2.
Two kinds of problems follow from that:

1. **Azimuth refuses the game.** It only accepts the games it knows, identified by file hashes
   and a per-game description built into `azimuth.exe`.
2. **The game and Azimuth speak slightly different APIs.** Interfaces changed between XDK
   versions: method tables have different layouts, some calls pack their arguments differently,
   some structures and enums changed, and a few runtime classes do not exist in the newer XDK.

The mod solves both problems at runtime, from inside the Azimuth process.

## Why a `winmm.dll` proxy

`azimuth.exe` imports `winmm.dll` statically, and `winmm.dll` is not a Windows "KnownDLL".
Windows therefore loads the copy that sits next to the executable first, before `WinMain` runs.
That gives the mod a point to run before Azimuth does anything, without modifying any file on
disk.

The proxy forwards every real `winmm.dll` export to the system copy in `System32`. The forwarding
table is generated by `tools/gen_winmm_stubs.py` into `winmm_stubs.S` and `winmm_exports.def`, so
Azimuth's own use of `winmm` keeps working.

Deleting `winmm.dll` restores the original Azimuth. FH2 is not affected by the mod.

## Guiding principle: verify, then patch, in memory only

Every change is made in memory, after Azimuth (and later the game) has been mapped:

- Before touching any location, the proxy checks the bytes that are there against the bytes it
  expects. If anything does not match (a different `azimuth.exe` build, a different game
  version), it changes nothing and logs why.
- The mod supports one exact `azimuth.exe` build (identified by SHA-256) and FM5 package
  version 1.0.0.20.
- Hooks are small detours: the original instructions are moved to a trampoline, and the detour
  jumps to a function in the proxy that can call the original.

## Startup sequence

1. **`DllMain` of the proxy.** It loads the real `winmm.dll`, reads `azimuth_fm5.ini`, opens
   `azimuth_fm5.log`, and checks that `azimuth.exe` is the expected build.
2. **Make Azimuth accept FM5.** The proxy builds a description of FM5 in memory, in the same
   format Azimuth uses for its own games (title, expected files and hashes, languages, options).
   It then adds that description to the list of games Azimuth accepts. A few checks that assume
   FH2's layout (for example around TLS and the XG texture library) are relaxed so that FM5
   passes them as well.
3. **Hook Azimuth's own entry points.** These are the places where the mod needs to step in later:
   the import resolver, the step where Azimuth patches the loaded game image, device creation,
   and a few others.
4. **Azimuth loads FM5.** When Azimuth reaches the step where it would apply its FH2-specific
   fixes to the game image, the hook runs the FM5 fixes instead: options from the ini, language
   and speech handling, and the launcher's graphics settings.

## Bridging XDK differences

Most of the work is in this layer. FM5 calls interfaces in the 2012 XDK layout, and Azimuth
implements them in FH2's layout. The proxy translates in between.

### Direct3D 11.X (`d3d_fm5.c`, generated `d3d_thunks.S`)

- **Device creation.** FM5 asks for a device creation function that Azimuth does not export under
  that name. The import resolver hook supplies one that creates the device through Azimuth.
- **Device method table.** The older XDK lacks a few methods that the newer one has, so every
  later method is shifted. The proxy gives FM5 a method table in FM5's layout that forwards each
  slot to the correct Azimuth method.
- **Device context.** In the older XDK, the context exposes a second method table embedded in the
  object itself, at a place where Azimuth keeps internal state. The proxy therefore hands FM5 a
  separate context object with its own tables, and forwards to Azimuth's real context. The
  per-slot forwarding thunks are generated by `tools/gen_d3d_thunks.py`. Slots fall into three
  kinds: direct forward, forward through a C wrapper that converts arguments, or no equivalent.
- **Argument and structure conversions.** Examples: draw calls whose arguments are packed
  differently, "fast" resource setters that become the standard setters, primitive topology
  (inlined in the newer XDK, so Azimuth has no method for it), and the swap chain present
  parameters.
- **MSAA and ESRAM.** FM5 aliases render targets in the console's ESRAM in ways FH2 does not, and
  uses MSAA resources (including FMASK) that need resolving. The proxy emulates the aliasing and
  handles resolves, `GetDesc` results and resource lifetimes so that the scene, the garage and
  the save thumbnails render correctly.
- **Lifetime fixes.** One example: protection against FM5 releasing shader bytecode twice when it
  goes back to the menu.

### XG texture library

FM5 uses its own copy of the console texture-layout library (`xg_x.dll`) with an older calling
convention. The proxy loads it and adapts the descriptor ABI, so texture address computations
match what the game expects.

### Audio (`shape_fm5.c` and the XAudio2 setup)

The console audio processor runs command graphs. FM5 builds graphs with the same fields as FH2,
but with a different opcode numbering. The proxy translates each graph in Azimuth's copy, never
in the game's memory, before Azimuth's interpreter runs it. XAudio2 creation is adapted as well.

### WinRT (`winrt_fm5.c`)

Some runtime classes FM5 activates exist only under older names or interfaces, mainly the
Kinect speech recognizer. Speech cannot be emulated, so the proxy activates a stub that reports
"no recognizer", and the game skips voice setup on its own.

### Diagnostics (`debug12_fm5.c`)

With `D3D12Debug=1` (or `2`) in `debug.ini` (section `[Debug]`), the proxy enables the Direct3D 12
debug layer under Azimuth and writes every validation message to `azimuth_fm5.log` as it happens.
`debug.ini` holds development-only diagnostics (`D3D12Debug`, `DrawSkip`, `DrawSkipHashes`), applies
to every game the proxy handles and is not shipped in the release.

## Options

`azimuth_fm5.ini`, section `[FM5]`, is read at startup. Each option is applied by patches in the
game image or by hooks:

| Option | Effect |
|---|---|
| `SkipIntro` | Skips the opening studio videos. |
| `SkipPresentationVideo` | Skips the presentation video shown before the first race. |
| `UnlockDLC` | Treats the DLC content already included in the game as owned. |
| `EnableMarketplace` | Enables the Marketplace menu without Xbox Live (shows the DLC packs). |

The Azimuth launcher's graphics settings also apply to FM5. Resolution and frame rate are passed
through. Car detail, shadows and reflections are mapped onto FM5's own render settings
(`gfx_fm5.c`).

## Source layout

| Path | Contents |
|---|---|
| `winmm_proxy/fm5_patch.c` | Entry point, `winmm` forwarding setup, ini, FM5 game description, Azimuth patches and hooks, FM5 image patches |
| `winmm_proxy/d3d_fm5.c` | Direct3D 11.X bridge (device, context proxy, conversions, MSAA/ESRAM, present) |
| `winmm_proxy/gfx_fm5.c` | Launcher graphics options mapped onto FM5 render settings |
| `winmm_proxy/shape_fm5.c` | Audio graph opcode translation |
| `winmm_proxy/winrt_fm5.c` | WinRT activation stubs |
| `winmm_proxy/debug12_fm5.c` | D3D12 debug layer hook |
| `winmm_proxy/d3d_thunks.S`, `winmm_stubs.S`, `winmm_exports.def` | Generated by `tools/gen_d3d_thunks.py` and `tools/gen_winmm_stubs.py` |
| `winmm_proxy/tests/` | Unit tests for the proxy |
| `tools/` | Generators, the release README converter and the reverse-engineering helper scripts |

## Build and tests

`sh winmm_proxy/build.sh` builds `winmm_proxy/build/winmm.dll` with mingw-w64 gcc and then runs
the tests.

The tests (`winmm_proxy/tests/`) build a Windows executable that includes each proxy source file
directly, so they can reach its internal functions. They run without starting the game:

- **Always:** the patch and hook helpers, the FM5 game description layout, and the D3D, graphics
  and audio translations against fake Azimuth objects.
- **With your own copies of `azimuth.exe` and the FM5 executable present** (they are never part of
  the repository): the full install and FM5 patch steps run against mapped copies of the real
  binaries. Every expected original byte and every written byte is checked. Without the binaries,
  these tests are skipped.

GitHub Actions (`.github/workflows/ci.yml`, Windows runner) runs the tests on every pull request.
On a `v*` tag push, it runs the tests, then builds and publishes a release zip containing
`winmm.dll`, `azimuth_fm5.ini` and `README.txt`.

## What is not in this repository

- Azimuth itself, its data folder, and any game files.
- Any code from Azimuth or from the game: no decompiled or disassembled snippets.
- The detailed reverse-engineering notes. They are kept privately.
